# 新增城市与商圈的完整工作方法

本流程把广州、苏州、上海的店单研究、现场图集和网图补充整理成可重复执行的方法。以后新增城市、给已有城市补商圈，或只补某一模块，都从这里开始。字段细节见 [城市归档填写指南](city-data.md)，营业分类遵守 [店铺一览固定维护规则](shop-directory-rules.md)。

## 1. 先确认单位与交付范围

2026-10-27展示口径补充：快闪、慢闪及本期限时主题统一称“快闪活动”，以项计数，不计入常规门店；原有`limited`字段及档期处理沿用。官方店铺栏列出并有可靠本址经营线索的，可结合两项依据确认营业，账号缺失不单独降级；待核候选与异店证据继续按[固定维护规则](shop-directory-rules.md)处理。

先建立“城市 → 商圈／独立地点 → 圈内门店 → 素材”的对应关系。榜单中的商圈是一个地点，有自己的稳定 `place.id`；商圈内的谷店属于这个地点的店单，不需要为每一家都创建榜单卡片。值得独立评价的单店可以另建地点，避免误把同名连锁的不同分店合并。

每个地点默认检查以下模块，有材料就接入，暂缺则记录缺口，不填假内容占位：

| 模块 | 本轮应完成的内容 | 接入位置 |
| --- | --- | --- |
| 地点与地图 | 正式名称、别名、地址、城市颜色、作者评价与排名 | `places.json`、`site.json` |
| 谷店一览 | 逐店名称、位置、主营、营业依据、官方账号与不确定项 | `shop-directories.json[place.id]` |
| 现场图集 | 作者照片／视频、清晰图注、拍摄日期与地点归属 | `places.json` 的 `gallery` |
| 网图补充 | 经核对的真实照片、原始图文出处、发布日期和用途 | 同一 `gallery`，附来源字段；另存来源清单 |
| 视频章节（有素材时） | B 站视频及对应地点片段 | 按 [B 站章节实施说明](bilibili-chapters.md) 接入 |
| 研究与验收 | 来源、取舍、覆盖情况、缺口、桌面／手机检查 | 原商圈研究报告；新地点才建目录 |

开始前先找到原商圈报告；有记录就在原文件增量更新，新地点才使用[城市研究工作单](templates/city-research.md)建立报告。检查工作区已有修改，保留用户现有评价、评级、顺序和素材；补图或查资料不自动改变实地体验。

## 2. 建立城市与稳定地点

1. 在 `rank/src/data/places.json` 增加城市键或复用已有城市，每个地点保留全站唯一 ID，例如 `chengdu-shop-001`；改名、补图或重访不换 ID。
2. 在 `rank/src/data/site.json.cityColors` 固定该城市的颜色，不与已有城市重复。城市名称必须与数据外层键一致。
3. 地点的档位、全榜同档顺序、评价和到访日期由作者提供。不同城市同档的 `order` 也不能重复；没有作者评级时先保持 `published: false`，不要拿网评代替作者体验。
4. 先填可靠的文字地址；确认 WGS84 坐标后再填坐标对象。不把百度／高德坐标直接标成 WGS84。商圈分区、旧名和常见别名按实际资料补充，避免搜索漏项。

地点骨架见 `city-data.md`。未知封面、地址、到访日期可用 `null`，暂缺图集用 `[]`，不虚构坐标和日期。

## 3. 逐店研究：先限定近两年，再核对营业与账号

资料窗口采用研究当年与上一年；2026年研究采用2025-01-01至实际研究日的资料，后续随年份推进。2025年以前的帖子与网图不作为当前营业店单或新补图依据，通常只留研究档案；证明停止营业历史所需的原经营／原位置／关闭来源可附于历史条目，不视作当前经营确认；无近期来源的旧店不为凑数放进“展开更多”。当前仍可读取的官网门店目录属于持续维护的信息，可核对后使用，但不捏造发布日期。

查店必须执行 [店铺发现与账号核对流程](shop-account-research.md)：先在小红书、抖音分别做商圈范围的内容发现，再合并候选、逐店核实账号与分店，最后按楼层及来源差异补漏。攻略不是完整名单；缺少任一必要渠道或步骤时明确交付阶段性结果，不能把“给已知店名找账号”写成“店铺查找完成”。停止条件和最小台账以该流程为准，复用原证据并只针对缺口追加查询。

维护已有内容时，原网页的店铺、账号与来源只核对是否对应本分店，保留原读取日，不重新搜索一遍。已有双平台发现及有效经营证据直接引用；新候选、失效或冲突来源和明确缺口才追加检索。重试浏览器、恢复额度或整理文档本身不构成重跑研究的理由，也不刷新营业核对日期。

对每个商圈分别搜索，不能只凭城市总攻略覆盖全部分店。可复用的查询组合：

```text
城市 + 商圈全名 + 谷店／楼层／店铺一览
城市 + 商圈旧名或别名 + 探店
品牌名 + 城市 + 商圈名 + 官方／店铺／地址
门店名 + 闭店／搬迁／装修／营业时间
商圈名 + 近期月份／节假日 + 上新／开业
```

优先读取品牌官网门店页、商场官方导览、门店官方账号，再补小红书／抖音原帖、探店评论和报道。搜索摘要只用于找入口，实际采用的结论要能对应已读正文、图像或公告。记录原文链接、发布者、发表时间、核对时间和它能支持的结论；页面打不开就标为未核对，不宣称已经读过。

小红书按用户要求低频、串行，每次只针对一个明确缺口，优先复用已打开页面，不批量穷举、并发或频繁刷新。内容与用户模式按实际页面分别记录；遇登录、验证码或安全限制立即停止相关操作并请用户处理，不用其他入口绕过，恢复后续写原报告。具体要求见[发现与账号流程](shop-account-research.md)。

逐店核对四件事：是否是这个城市这家分店、是否有营业确认、位置依据来自哪里、主营依据来自哪里。品牌全国账号标为 `scope: "brand"`，不能把其他城市分店账号当成本店账号。已公布的搬迁、闭店、限时活动要保留适用日期，后续更新先复查这些变化。

### 营业展示采用固定判断

| 可确认情况 | 数据处理 | 页面展示 |
| --- | --- | --- |
| 本人账号主体、分店与有效经营依据均已核对，无未解关闭冲突 | 填写 `accounts`，保留 `sources` | 默认展示，营业中；仅核到身份的候选号暂记报告／来源，不填会自动升级营业的accounts |
| 官方店单／官网明确列出本店仍营业 | 填 `operatingConfirmation: "official-listing"`，把核对依据写入 `note` 与 `sources` | 默认展示，营业中；不要求另有社交账号 |
| 仅有近两年探店、店单、位置简介或商品介绍 | 保留 `sources`，不添加营业确认字段 | 默认收起，展开更多中显示有营业线索 |
| 原在营门店彻底关闭或迁往另一地点的旧址 | `status: "closed"`＋`inactive.reason: "closed"`或`"relocated"`，保留原位置、历史和出处 | 单列停止营业，标签“已停止营业”；新地点正常维护，同商场换楼层不按外迁处理 |
| 原在营门店因装修暂时关闭／停业原因或旧址保留情况未明 | `status: "closed"`＋`inactive.reason: "renovation"`或`"unconfirmed"` | 单列历史，分别显示“装修停业”／“停业待核实”，不计当前营业或普通待核实 |
| 已结束主题／未选入历史栏的闭店或失效旧名单 | `status: "closed"`，保留原始依据归档 | 前台隐藏，不计“展开更多”；主题结束不能宣布整店停业，不批量恢复旧名单 |

`status` 的 `recent/listed/older/unverified` 保存研究状态，并不直接等于前台“营业中”；当前分类由 `shopDisplayStatus()` 统一执行。不要仅把 `status` 改成 `recent` 就认为确认完成，也不要为普通帖子伪造官方账号。官方明确确认在本项目按确定营业处理，不额外计算或展示未经定义的置信度百分比。

账号存在和历史官方店单也需要在后续研究时检查关联分店与闭店冲突。新核实必须保留真实依据；复查没有完成时，不仅为“显得新”更新核对日期。

### 标准店单格式

快闪、慢闪、明确限时开放或本期限时主题另填`limited`，由共享组件单列“限时谷店／快闪”，与“常规谷店”分开；两栏未确认线索各自默认折叠。例如：`"limited": { "scope": "theme", "period": "2026-10-01 至 2026-11-01", "startsOn": "2026-10-01", "endsOn": "2026-11-01" }`。整家临时店用`scope: "store"`；年份／日期不明只写原文`period`。普通促销、每日营业时段和试营业不自动构成限时店。主题到期只结束这一期记录，不推断常设店整体关闭；已知结束日早于`checkedAt`的条目须隐藏归档。每轮按常规确认、限时确认、各栏待核实、停止营业历史及隐藏归档分别统计；格式调整不刷新营业复核日期。

以下是写入 `rank/src/data/shop-directories.json` 的结构示例。占位名称、日期和 `example.com` 均须替换为实际资料后才能投入使用；没有 `kindSources`、`accounts` 或官方确认时省略对应字段。

```json
{
  "chengdu-shop-001": {
    "area": "商圈或分区名称",
    "checkedAt": "2026-10-17",
    "shops": [
      {
        "name": "门店正式名称",
        "floor": "负一层",
        "kind": "动漫周边、模型、寄售周边（含已核实的作品）",
        "status": "listed",
        "operatingConfirmation": "official-listing",
        "note": "官方门店页列出本商圈分店及位置；注明需要保留的营业或搬迁信息。",
        "sources": [
          {
            "label": "品牌官方门店页",
            "url": "https://example.com/stores"
          }
        ],
        "kindSources": [
          {
            "label": "门店商品介绍",
            "url": "https://example.com/products"
          }
        ]
      }
    ]
  }
}
```

主营用短品类列表、顿号分隔，作品／合作方用括号补充；保留国谷、日谷、中古、寄售、联动等有依据的区别，不把“出现过某作品”写成专营。楼层统一用中文，LG 等商场原标识按原样保留。未知位置或主营省略字段，不按店名猜测，也不凭铺号首位推楼层。

`note` 解释证据和冲突，`sources` 支持营业／位置，`kindSources` 支持主营，三者用途不同。`sources.date` 填真实完整发布日期；按用户2026-10-19确认，小红书／抖音发表日仅显示月日时按实际读取当年补年，原标签与理由存台账。正文月日结合发表日期、明确年份和预告／回顾上下文判断活动年份；跨年仍有歧义则保留原文。只有编辑时间或时间范围时用 `dateLabel`，两者不同时写；无日期就省略，不把`checkedAt`当发布日期。可靠旧研究若实际明确指向本商圈分店，可复用并提高相应事实证据强度，见[账号核对流程](shop-account-research.md)。

常规谷店有小红书／抖音账号时隐藏文字依据及两类来源列表、保留账号入口；常规无账号时，包括由官方店单确认营业者，均显示原文字说明与出处链接。限时栏沿用营业中隐藏来源列表、待核实显示的规则。停止营业历史不适用“有账号隐藏依据”：始终显示原位置、历史、原因、文字说明、合并出处及原账号；未选入历史栏的闭店记录和已结束主题仍隐藏。详细规则以 `shop-directory-rules.md` 为准。

历史条目使用`inactive: { reason, history }`，原楼层／铺位存`floor`（不加重复的“原位置”前缀）。已知停止日才可写“～2026.10.1”等截止时间；只知道最后一次经营记录就保留“某日有经营记录；停止时间待核”，公告日／编辑日／用户反馈日不冒充撤店日。装修期间说明会继续开，按装修停业；同商场换层复业后移除inactive，当前条目只保留新位置；外迁旧址历史写明有据去向，不影响新店。

## 4. 现场图集：按地点匹配，再按用途组织

先盘点用户原始照片和视频，按可辨识门头、楼层、建筑、拍摄顺序或作者说明匹配地点。无法确认地点的素材保留待核，不凭相似装修硬配。作者的 `visitedAt` 是实际到访日期，不随补图、网图抓取或研究日期变化。

每个地点优先沿用现有图集分组。新地点默认按下列顺序组织，只创建有素材的分组：

| 分组 | 能说明什么 |
| --- | --- |
| 商圈外部 | 商圈建筑、入口、周边与抵达辨识 |
| 店铺外景 | 店名、门头、所在楼层和通道 |
| 店铺内景 | 货架、寄售区、商品品类与空间布局 |
| 额外活动 | 集市、快闪、舞台等当时发生的活动 |

保留有信息价值的不同角度，去掉重复导出、近似连拍和无法辨认的片段。视频可与照片放在同一分组；使用本地 MP4，必要时提供封面。图注写“画面里可见什么”，不把镜头中一排货架外推成全店品类或实时库存。

## 5. 网图收集：补足缺口，并建立逐图来源记录

先排除资料窗口以外的帖子及网图（本轮2025年以前），再列每个地点欠缺的外观、门头、内景或活动图，针对缺口搜索；不为凑数量重复下载。优先选择原作者／门店／商场官方发布及出处明确的报道。找到搜索缩略图后回到原始图文页，核对图片对应的城市、商圈、分店和时间，再选用。

每张拟采用图片至少完成以下检查：

- 读取来源正文并查看图片，能说明为何对应本地点；地点不能确定就不接入。
- 保留来源名称、原始图文链接和可确认的发布日期；拍摄日期、发布日期、活动日期、采集日期分别记录，未知用 `null`，不能混填。
- 去重时同时检查文件哈希和画面内容，同图不同尺寸、转载或裁切也要识别；原件和展示副本哈希可分别保存。
- 保留已有水印、画面上下文和可见署名；展示副本只做必要的等比例缩放、格式与体积优化。不要用 AI 重绘图冒充现场图。
- 有效窗口内的历史活动图在图注明确“历史活动”；早于窗口的旧图仅归档不接入；未标日期的官网照片只有核实为当前门店展示时才可采用并说明“未标发布日期”；网图不充当作者实拍或当前营业、库存、优惠确认。
- 记录使用范围或来源限制；无法取得可用图片时保留原文链接和缺口，不用搜索缩略图冒充已获取原图。出处链接本身不代表取得额外授权。

本项目已有真实照片与来源管理方式，不需要为新城市重新设计图片系统。网图按内容进入原有四类，用图注和来源区分，不必为同一张图重复建立“现场”和“网图”两份条目。

### 素材路径与展示字段

```text
rank/public/images/places/<CitySlug>/<PlaceSlug>/现场素材/
rank/public/images/places/<CitySlug>/<PlaceSlug>/网图补充/
docs/research/<city>-<YYYYMMDD>/report.md
docs/research/<city>-<YYYYMMDD>/sources.json
```

这是新建目录的建议约定；已有目录继续沿用，不为统一目录名移动旧素材。`src` 写从 `rank/public/` 开始的相对路径，不包含 `public/`，大小写必须完全匹配。日期与审核记录放研究文档，不增加未经类型定义的页面字段。

```json
[
  {
    "src": "images/places/Chengdu/place-a/现场素材/interior-01.webp",
    "alt": "门店寄售区货架（作者实拍）",
    "group": "店铺内景",
    "sourceName": "作者实拍（填写真实拍摄日期）"
  },
  {
    "src": "images/places/Chengdu/place-a/网图补充/exterior-01.webp",
    "alt": "商圈建筑外观（网图；填写来源日期或未标发布日期）",
    "group": "商圈外部",
    "sourceName": "原发布者／媒体名称（来源日期）",
    "sourceUrl": "https://example.com/original-post"
  }
]
```

这是 `gallery` 内容示例，不是独立生产数据；先替换占位内容并放入实际文件。视频增加 `type: "video"` 和 MP4 `src`，可选 `poster`。当前页面媒体类型没有单独的日期字段，日期在 `sourceName`／`alt` 说明，完整信息放研究清单。

研究 `sources.json` 的每张网图建议保存 `placeId`、`src`、`alt`、`group`、`sourceName`、`sourceUrl`、`sourceDate`、`eventDate`、`originalImageUrl`、`originalSha256`、`localSha256`、`evidence`、`reviewMethod`、`reviewedAt` 和 `processing`；拍摄日期已知时另记 `capturedAt`。这份文件是研究台账，不直接导入页面。可参考 [上海补图来源清单](research/shanghai-web-images-20261017/sources.json) 与配套 [报告](research/shanghai-web-images-20261017/report.md)。

## 6. 接入页面，形成同一条数据链

```text
城市颜色 ─ site.json.cityColors[城市]
地点卡片／地图／详情 ─ places.json[城市] → place.id
谷店一览 ─ shop-directories.json[place.id]
现场照片／网图／视频 ─ place.gallery → 本地 src 与来源说明
内容／图集／地图更新 ─ updates.json → placeIds
```

`PlaceDetail.vue` 已按 `place.id` 关联店单，有店单就展示谷店一览，有非空 `gallery` 就展示现场图集；图集分组和来源由 `PlaceGallery.vue` 读取。因此多数新增城市工作是填数据、加素材和研究记录，无需复制一份城市专用组件。新模块确实超出现有字段时再修改类型、验证器与共享组件。

地点 `updatedAt` 按实际内容修改更新；`visitedAt` 按实际到访保留；店单 `checkedAt` 仅随营业研究复核更新。单纯补网图不改变店铺营业分类和核对日期。更新记录使用现有 `added` 或 `edited` 类型及 `content/gallery/map` 分类，不发明新枚举；图集更新通常填 `category: "gallery"`，关联受影响的 `placeIds`。

## 7. 验收与完成条件

在 `rank/` 下使用项目要求的 Node.js 24 环境：

```powershell
npm run validate:data
npm test
npm run build
```

构建会生成媒体预览与在线播放副本，手动维护原始素材和数据，不手填生成索引。行为有改动时补充针对性检查；仅补文档无需运行整套构建。命令成功后做桌面与手机浏览器检查，至少覆盖 1440px 和 390px，以及新地点直达链接刷新。

| 验收对象 | 通过标准 |
| --- | --- |
| 城市与榜单 | 城市筛选、颜色、全榜同档顺序正确；评级符合作者提供内容 |
| 门店发现 | 小红书／抖音内容发现及官方渠道有实际记录；馆区／楼层缺口已补查；候选均有处置；受限或未完成时标阶段性结果，不承诺全商场无遗漏 |
| 谷店一览 | 常规／限时确认和停止营业历史各先5条，卡片下方按钮每次仅增5条，随新增卡片移动到末尾，余数不足5条补齐；待核实区初始关闭，展开后同样按5条递增；刷新／切换地点复位；搜索定位能展开到目标批次；未选入历史的闭店与已结束主题隐藏，失效旧名单仅归档 |
| 停止营业历史 | 四类原因标签与证据相符，独立计数；保留原位置、可核经营／停止时间、全部文字与原链接、原账号；不造日期，不把装修写成彻底关店、换楼层写成外迁，外迁不影响新址经营 |
| 来源展示 | 位置小字附店名旁、过长换行且不单开位置行；常规不显示作者到访；常规有账号隐藏重复文字依据，无账号（含官方店单确认者）保留说明和全部出处；同URL合并并保留标题／日期／支持范围；限时按固定规则，历史栏始终显示依据；后台证据完整 |
| 图集 | 分组正确，缩略图可见，点击可放大／播放／关闭；原图与来源链接正确；出处不被裁掉 |
| 日期与匹配 | 本地文件存在，照片确属本地点，来源日期与到访／研究日期不混淆，历史图有说明 |
| 地图与搜索 | 地址可用，地图与导航没有串店；地点别名、圈内店名搜索能关联正确商圈 |
| 响应式排版 | 总榜详情与地图介绍页均检查手机／平板／桌面；手机适配可用宽度，平板和桌面使用较宽内容区并随宽度增加列数；标题／位置／按钮／账号／长链接可读可操作，无横向溢出 |
| 更新与交付 | 报告列出覆盖数量、缺口和本轮实际核实范围；说明是否发布，不能把本地构建当成上线 |

研究报告按地点交付：当前营业确认／有效待核实数量、单列的停止营业历史数量，以及隐藏归档的闭店／过期记录数量；另列账号覆盖门店数、平台入口数及受限候选；现场照片与视频数量，新增网图数量，来源范围、时间及缺口。数字必须由本轮数据统计，没找到的写明原因，缺图或缺可靠证据不等于必须凑齐。

## 归档与清理

日常更新默认只维护**一份商圈报告＋独有证据**。已有目录继续沿用，恢复访问、补验、修正文案或同一轮续做不另建 `browser-recheck`、`rerun`、`final` 等过程目录。跨商圈验收结果分别写入对应报告，不另复制总报告。确有独立的新研究范围时再建立新批次，并链接原记录。

- **报告：** 保留当前结论、实际增量、来源引用、未解决项、验收日期／范围／结果和发布状态。失败后成功直接更新当前状态，必要时用一句话保留失败原因；避免旧“未完成”与新“通过”在正文互相矛盾。
- **证据：** 少量来源直接放报告；复杂研究可用一份 `evidence.json` 或已有 `sources.json`，每条保留原链接、发布者、原始日期、原读取日、分店关联和取舍。来源只存一次，正文及候选引用其ID。仅当日期判断、关闭冲突或图片内容无法由现有记录表达时留必要原文摘录／截图。已记录的事实不再搜索或下载。
- **候选：** 报告表格或一份台账即可。已写入生产店单且无额外研究信息的字段不整行复制；保留未接入候选、排除理由、冲突和下一步。数量、账号入口、当前店单和日期等可派生信息直接统计，不再另存多份JSON副本。
- **验收：** 同报告写明工具、数据版本／日期、尺寸、检查范围与实际结果；复杂测试最多附一份精简结果。截图按独特场景选择，通常每批0—2张即可；同页两尺寸、多次重试、相同大图不逐次留存。存在独立缺陷才酌情增加，正文解释用途。页面源码／DOM转储、长命令日志和成功后已被替代的失败截图不长期归档。素材内容证据与页面排版截图分开判断。
- **快照与脚本：** 不为每次内容更新保存全站数据或多轮 `before/final` 副本。仅有删除或改写独有来源时保存必要旧字段，已有归档足够就不再复制。一次性改数据／重放验收脚本执行后移除；可复用功能测试留在项目正式测试目录，不能把含旧店单的脚本当日常入口。
- **清理顺序：** 先确认文件用途及入站引用，把独有事实、原始日期、来源和未解决问题合并到保留位置；再删除重复记录、过期验收产物、一次性脚本和可重建缓存，同步修正Markdown及台账引用。不能仅因文件未被网页直接引用、年代较早或哈希相同就删除原始照片／视频、有效来源、作者设计稿、开发依赖或不同用途的必要素材副本。
- **生成目录：** `_site/`、`rank/dist/`、测试项目／结果及工具缓存可用现有 `scripts/clean-generated.mjs` 清理；先确认没有仍需保留的唯一文件。长期迁移基线和源证据应放维护文档／证据目录，不放临时测试结果目录。原件、唯一来源与Git历史保留。

仅修改文档或清理验收档案时，检查本地链接、剩余台账引用、来源保留与文件范围即可，不重跑完整浏览器研究。删除生成物不需要为证明清理成功重新生成同一批文件；涉及运行脚本或正式素材时执行与改动相应的检查。
