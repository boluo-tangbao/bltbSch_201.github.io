## 哪些问题确实需要同步测试

- 导航改为异步后，测试应等待目标 URL，而不是点击后立刻同步读取。这次确实存在测试时序问题，但实现中不必要的零毫秒定时器也一起修复了。
- 控件收纳、标签取消入口改变后，应同步更新操作路径与定位方式。本聊天中的标签／工具栏调整已经更新相关测试；上述 9 次云端失败并非由旧标签按钮断言触发。
- 新增 GIF 后需要补充开发预览覆盖。原来的“失败请求必须为空”规则没有过时，不应把该 GIF 加入忽略名单。

工作流配置 `.github/workflows/deploy.yml` 最近一次修改是 2026-11-08。上述失败主要通过修改实现、数据、预览服务和测试脚本解决，而非反复修改 Actions 工作流步骤。

## 本聊天中未被云端失败次数反映的问题

- 手机清单卡片盖住控制台：真实的层叠顺序问题。此前只看单个组件截图或检查宽度不足以发现；后来补了重叠区域实际命中控制台的浏览器检查，并覆盖选店底栏。
- 标签重复占一行：重复显示状态的界面设计遗漏，不是 CI 配置问题。
- 工具按钮的形态、颜色、字型、间距、蜡笔分隔：主要是视觉方案与用户偏好的反复校准，不能计作发布失败。
- 本地试跑时的 JSON 导入方式、命令工作目录、报告目录清理冲突：属于执行／测试维护失误，应在本地修正，不应与 GitHub Actions 云端缺陷混为一谈。

## 责任与交付问题

1. 配套实现没有一次做全：新资源类型、资源路径、活动配置和导航方式改变后，相关入口遗漏。
2. 验证范围描述不够明确：构建成功、若干专项通过、完整本地验收通过、云端发布成功，是四个不同状态。仅有前两项时，不能让使用者误以为整条发布链路已经确认。
3. 第一轮修复后未充分确认原故障条件：转场异常连续出现，说明局部补丁没有经过同条件闭环验证。
4. 后续提交重复携带已知问题：已有失败尚未解除时，新功能或素材提交继续触发同一故障，增加了用户对“不断产生新错误”的感受。

## 后续应采用的交付标准

- 素材／目录维护：一次检查所有活动配置缺项，核对资源引用和实际文件，不只修第一条报错。
- 公共页面与转场维护：同时覆盖静态组装、Vite 开发预览、手机布局、减少动态效果、正常导航和返回恢复。
- 检查顺序与 CI 对齐：单元测试 → 数据校验／类型检查／构建 → 网站组装 → 发布资源检查 → 主站／活动浏览器验收 → rank 浏览器验收。发布资源检查会清理验收报告目录，必须先于浏览器验收运行，不能并发执行。
- 运行环境：CI 使用 Linux Chromium；本机 Edge 的通过不能直接等同于云端 Chromium 已通过。需要在交付中说明实际运行的环境与范围。
- 修复针对缺陷本身；只有交互契约改变或断言时序错误时才调整测试，不移除零页面异常、零失败资源等有效门槛。
- 状态明确写为“专项通过／完整本地通过／云端通过／已发布”，不要用笼统的“检查通过”替代。
